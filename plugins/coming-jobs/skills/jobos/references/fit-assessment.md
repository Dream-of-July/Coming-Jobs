# 岗位适配独立评估

用于公司比较、每日推荐及重做推荐。先判断候选人能以什么证据承担哪些工作，再比较完整 JD；不按职称、行业热词或上一批排序替代判断。采集、实时目录核验和每日提交计数见 [完整采集与每日目标](discovery-and-daily-goals.md)。个人资料、方向、到岗窗口、证据与结论只存私有工作区，通用仓库不包含候选人样例。

## 先理解人

只读取已授权的当前简历、职业档案、归属记录、原始工作产物、个人项目、本人聊天原话与第三方反馈。区分本人提出的问题、决策和验证，与 Agent 的委派指令、总结和生成结果。项目共享不等于个人完成；AI 辅助原型不等于专业工程能力；概念不等于上线成果。

每条能力或偏好保留来源与等级：

| level | 证据 | 边界 |
|---|---|---|
| self_statement | 本人原话、明确纠正 | 可记录事实和偏好，不能代替成果证明 |
| original_artifact | 归属可核验的原始产物、版本、研究记录 | 写清本人贡献及可追溯位置 |
| third_party | 导师、评审等反馈原文 | 区分原文与 AI 转述；不推断面试结果 |
| ai_summary | AI 生成的画像、审计或复盘 | 只作线索，回到原始资料核验 |
| inference | 缺少直接依据的推断 | 转化为会改变结论的问题；不能支撑“优先” |

先写下证据最支持的三类工作、各自边界、容易误判的工作及非显性的个人资产。不为证明用户的自我定位而挑证据。工具和领域能力逐项标 breadth / depth / none 及证据等级；截图、清单或兴趣只证明接触广度，不能证明熟练度、深度或投入时长。

在私有 `profile(fit_context)` 保存结构化毕业年份、到岗与能力：`availability.current_location` 是当前所在地，`location` 是已确认可到岗地点，两者不互相推断；`earliest_start`、`days_per_week`、`continuous_months` 未知就留空。补充到岗字段按键合并；能力按名称更新，保留其他已确认项。岗位的 `availability.latest_start` 是必须到岗的最晚日期。留学、在读或住在某地本身，不能证明能全职到岗或不能迁移。

## 逐岗判断

全部岗位先分类；与方向相关或正文含相关职责的岗位精读完整职责与要求，其余按正文交叉检查藏在相邻职能中的机会。报告分类、精读、排除和未读数量及依据，不把下载数称为精读数。对每岗回答：

1. **服务谁**：个人用户、企业员工、内部团队、开发者、玩家、商家、混合或不明。按实际任务判断；“产品”“体验”“AI”不证明面向消费者。
2. **核心交付**：产品方案、交互、视觉、研究、代码、运营、内容或混合。区分用研究/原型作为方法与专职研究/工程交付。
3. **硬门槛**：逐项核查毕业届别、学历、专业、语言证明、工具/引擎、作品集、到岗、城市和名额。只有要求栏和结构化字段能导致资格失败；“优先”“加分”始终是 preferred。职责不能冒充任职要求。
4. **证据对应**：引用 JD 条目的要点，将任务映射到具体产物、本人贡献、来源及证据等级；同时写出缺口，避免“经历丰富”等无判断力理由。
5. **建议与位置**：为何排在此处、相比相邻岗位强在哪里、补齐什么会改变档位。宿主在同公司和项目内提供独立的rank序号及具体reason，说明相邻岗位为何前后；rank是顺序，不是匹配分数。不要用职称替代职责，不用匹配分数或录用概率制造精确感。

`hard_gates` 保存 gate、source、status、note，可附 requirement_id；`evidence_refs` 保存 evidence_id 与 level。缺少新字段的旧评估保守读为 unknown，等待重新评估，不能把旧 score 转为新资格结论。

硬门槛状态：meets / fails / unknown / conflict。只要存在未知或冲突，进入资格待澄清；独立、已核实的其他硬性失败仍可排除。学历代码与正文冲突须保留两侧证据，不能直接 pass/fail。可依据同一项目正文与代码的对应关系提出代码解释，但标“推断”、保留原值，不能把解释变成已确认资格。接口项目与正文招聘类型冲突同样保留，按正文对应流程核验。一个父入口多个方向须明确推荐分支，不夸大投递名额。

| tier | 用法 |
|---|---|
| priority | 职责对口、硬门槛已满足，并有非推断的直接证据 |
| conditional | 有可说明的能力、方向或经验短板；已核实资格不失败 |
| adjacent | 相邻职能备选，明确不同的核心交付 |
| qualification_hold | 资格未知、冲突，或缺少必要评估信息；不进可行动推荐 |
| misjudged | 职称看似相近、实际对象/交付不对口；单列解释 |
| excluded | 已核实硬性不符，含实习到岗冲突或届别不符 |

默认不把面向开发者、内部团队或代码交付的岗位放入优先。若本人明确的方向和非推断证据支持例外，可如实解释，不能把某位候选人的偏好写成所有人的永久禁令。工具只校验结构与门槛；JD语义、贡献归属与真正工作质量仍由宿主核实。

## 投递规则与已有申请

推荐前读取公司/项目规则及已有申请的岗位、原始阶段与观察时间。使用机会账本保存 limit、can_change、volunteer_order、deadline、source/source_ref、observed_at。核验超过7天或缺失时显示“未复核”。撤回、被拒不自动返还名额；资格好的岗位也不能掩盖额度耗尽。名额用完只作参考，已投岗位及同父入口不重复推荐。规则/项目不明确则保留核验问题，不能猜测一人仅一岗或已恢复名额。

## 独立排序、恢复与差异

重新评估时，在读取旧推荐前完成并保存带时间戳、哈希和证据引用的独立排序。`comparison(seal)` 固化快照后，才允许 `previous` 读取旧批次。只因新证据修改，保留原因；差异分“漏掉、高估、低估、相同”，逐项说明职责、门槛或证据为什么改变结论。不能为制造差异而改序。

公司比较用 `jobos1_comparison`：start → next → ingest/observe/assess 分批续跑 → seal → previous（如需比较）→ report。独立的最多20家公司、累计正文/评估预算与游标；重复 start 不重置。未完成只能报告 partial 和缺口。它不生成日报 A–E 编号、不占用/重置 daily_budget，也不创建申请。每日入口继续沿用五家公司上限；在当日独立排序快照保存后才能比较旧推荐。

## 输出与收尾

先用不超过五点交代结论，再说明读过的材料、证据等级、未读部分及采集范围。每家公司分开正式校招与实习，使用七列：

| 公司与官网岗位 | 城市及招聘项目 | 实际工作与服务对象 | 对应经历 | 不匹配与硬门槛 | 建议与理由 | 官网链接 |
|---|---|---|---|---|---|---|

保留资格待澄清/名额用完的参考区、误判清单、会改变结论的问题，以及与上一批的四类差异。问题写明影响哪些岗位；回答后只更新受影响部分并注明日期。岗位不足不凑数，行数不代表投递数。本流程不填写、不上传、不提交申请；后续选定仍走独立的材料审核与人工最终提交。
